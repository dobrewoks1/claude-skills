# Фазы 1-2: разведка источников и сборка базы брендов

## Протокол API-first (главный урок конвейера)

Прежде чем писать парсер DOM или сажать браузерного субагента — потрать 15 минут:

1. Открой страницу источника в браузер-панели, вкладка network (или `read_network_requests`).
2. Ищи XHR-запросы к `*api*`-доменам при скролле/переключении вкладок — так видно, отдаются
   ли данные через API. Дальше — документация площадки: есть ли официальный доступ, как
   получить свой ключ, какие условия и лимиты. Чужие ключи из HTML страницы не используем.
3. Проверь 2-3 запросами из PowerShell (`Invoke-RestMethod`): структура, лимиты, пагинация.
4. Сверь цифры API с тем, что видно на живой странице ГЛАЗАМИ. Если не сходится — ищи
   фильтр видимости (см. is_rated ниже), а не «чини» цифры.

Браузерный субагент — только когда API нет или он закрыт, и только в рамках условий площадки.
Он в десятки раз медленнее, ошибается в сортировках и жжёт контекст (см. `06-делегирование.md`).

## 2ГИС

### Каталог (точки) — всегда свежий сбор

**Каждый рейтинг начинается со свежего прогона сборщика, старые CSV не переиспользуются.**
Данные дрейфуют за недели (умирают заявленные каналы, меняются рейтинги и часы) — а замер
строится именно на «компания сама заявила этот канал сегодня». Устаревшая строка = ложное
обвинение или ложная похвала.

Готовый сборщик: `<путь к сборщику каталога 2ГИС>` — официальный Catalog API
2ГИС (region/search → rubric/search → /3.0/items), гео-дробление против лимитов, дедуп по
2gis_id, выгрузка CSV+JSON+SQLite, retry/rate-limit из коробки. Ключ — свой, из кабинета
разработчика 2ГИС (хранится в `.env`, не в git). Читай README сборщика и:
```bash
node src/index.js collect ...      # сбор по нишам города, параметры в README
```
Одна ниша ≠ одна рубрика («стоматологии» = поликлиники + частные) — сборщик резолвит набор
рубрик сам, но проверь глазами его выбор для новой ниши.

Старые выгрузки `<путь к эталонной реализации>\база\*.csv` — только образец схемы колонок (название, адрес,
телефон, сайт, 2gis, рейтинг, отзывов, часы, tg/vk/wa/max, email + процессные колонки) и
подтверждение, что метод работает. Данные оттуда в новый рейтинг не берём.

### API отзывов 2ГИС (проверен в работе 07.2026)
```
https://public-api.reviews.2gis.com/2.0/branches/<branch_id>/reviews
    ?limit=50&sort_by=date_created&key=<KEY>&locale=ru_RU
```
- **Ключ** `<KEY>` — только собственный, полученный у 2ГИС (кабинет разработчика или договор),
  и только если условия использования допускают такой сбор. Ключи, найденные в HTML чужих
  страниц, не используем; значения ключей не попадают ни в репозиторий, ни в отчёты — только в `.env`.
- `limit` максимум 50; пагинация — `meta.next_link` (курсор `offset_date`), глубина любая.
- **Сортировка обязательно `date_created`** — дефолтная «по доверию» мешает даты и ломает
  любые «ответы из последних N».
- Поля отзыва: `date_created`, `rating`, `text`, `is_hidden`, `is_rated`, `on_moderation`,
  `official_answer{date_created,...}` (пары «отзыв→ответ» дают скорость реакции!), `photos`,
  `provider`, `user.reviews_count`.
- **Фильтр видимости: `not is_hidden and is_rated`.** Публичная лента показывает только
  is_rated=true; API отдаёт больше. Считаем строго то, что видит посетитель, иначе владелец
  откроет карточку и цифры не сойдутся (проверено спот-чеком: rated-десятка = браузерной 1-в-1).
- Темп: пауза ~1.2 с между запросами (бережно, ниже любых лимитов); 229 брендов на глубину
  100 отзывов/365 дней ≈ 15 минут.
- meta отдаёт `branch_rating` и `branch_reviews_count` — сверяй с каталожной выгрузкой,
  расхождение ≥0.3 звезды = каталог устарел, истина за API.

Эталонный сборщик: `инструменты\аудит_2gis_отзывы.py` (пагинация, метрики скорости ответа,
потока за 90/180 дней, негатива, сырьё в пруфы). Переносится на любую нишу почти без правок.

## Яндекс.Карты
Парсится из карточки (рейтинг, оценки, отзывы, фото, награда «Хорошее место»), но капчи
агрессивные и покрытие будет неполным — это нормально, непокрытое честно уходит в н.д.
Не строй блок методики на источнике, который не можешь гарантированно собрать.

## Что скриптами НЕ достаётся (проверено)
- **ВКонтакте**: стена сообщества без логина не отдаётся ни на m.vk.com, ни на vk.com
  (обе — страница логина). Даты последних постов — только руками пользователя или через
  залогиненный браузер. Планируй это как ручной пункт с самого начала.
- **Нишевые агрегаторы** часто ограничивают частоту запросов и блокируют автоматический сбор
  уже после нескольких десятков обращений. Ограничения площадки не обходим (никакой смены IP,
  решения капч и маскировки скрипта под человека). План Б: снизить темп, поискать
  официальный API или партнёрский доступ, проверить короткий список вручную — остальное
  честно уходит в н.д. и не попадает в веса (см. `04-пассивные-слои.md`).

## Склейка точек в бренды (2 ступени)

Единица рейтинга — бренд, не филиал. Иначе сеть из 6 точек займёт 6 строк.

1. **Ступень 1 — телефон**: общий номер = один бренд. Надёжно.
2. **Ступень 2 — тёзки**: одинаковое имя склеивается ТОЛЬКО при (общий населённый пункт) И
   (общий домен сайта ИЛИ общий слаг мессенджера). Без этого «Улыбка» из трёх городов
   склеится в франкен-бренд (реальный баг, стоил места №7 в рейтинге).
3. **GENERIC-guard**: типовые имена («Стоматологическое отделение», «Стоматология», в
   недвижимости будут «Агентство недвижимости», «АН») не склеиваются по имени вообще.

Флагманский филиал бренда — с максимумом отзывов; gid флагмана = ключ бренда везде.

## Сегмент вне зачёта
Определи с пользователем в фазе 0 (гос, филиалы федеральных сетей, витрины-агрегаторы).
Записи остаются в базе с меткой (`sector`), но: place=None, нет в волне, нет в скоркартах,
нет в агрегатах. Формулировка агрегатов — «частные/независимые X города».

## Freeze
После старта волны база и данные волны заморожены (консоль ключуется по №). Дрейф источника
после заморозки — норма (клиника удалила канал и т.п.): сверяйся по gid волны, не пересчётом.
